## 已有能力，不重复列成“完全没做”

- 模型已走 OpenAI Responses 兼容 API；DSH/BackendTeam 保留 Agent 循环。Codex App Server 已非当前路线。
- 官方 Spec Kit 接入、需求/设计文档、基本审批哈希检查已存在。
- 聊天 workflow/status、接回与搁置、暂停/继续、意见输入、逐题确认、右侧资源预览有实现。
- 受控文件写入、Node 测试、切片交接、部分故障恢复和演示交付有证据。
- 本地 PostgreSQL、DbGate 和迁移有真实局部验收。

## 不算本次遗漏

- 用户明确暂缓的 Intel 云端验收：保留为延期，不重新要求现在完成。
- Linux/Windows、生产数据库和生产部署：原 V1 排除。Bundle 的发布就绪与用户业务的生产部署是两回事。
- 新旧会话里的 Codex App Server 讨论：之后用户改选模型 API，不再按旧路线继续建设。
- 最近提出但尚未确认原型的任务页签布局：是补齐任务可见性的候选实现，不冒充已经确认的视觉方案。

## 优先修复顺序与完成要求

1. R01–R06：任务列表、归属、切换、变更与审批来源。跨会话/归档后可见；查看不触发执行；新需求绝不能继承旧批准；取消和重启可恢复。
2. R07/R12/R14：用真实客户跟进新任务走通需求→设计→确认→开发→验证。旧任务保留；环境错误给出实际原因及可执行恢复，不让用户找虚构入口。
3. R08–R11/R13：把底层能力接到生产主流程；分别完成新项目、已有项目、子委派、通用检查和数据库恢复的适用验收。
4. R15–R18：补完整交互验证、图片入口、模型额度及未延期的发布门槛。

每项完成必须同时记录实现入口、实际验证场景和仍有限制；“代码存在”“测试通过”“用户主流程可用”分别判断。此核查不宣称穷尽所有缺陷，也不把待核实能力写成确定不存在。
