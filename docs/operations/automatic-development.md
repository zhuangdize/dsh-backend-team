# 什么是自动开发

“自动开发”指的是：用户确认需求、后端架构和数据库设计后，Backend Agent Team 按已批准的方案，在目标项目工作区完成一组连续工作：修改 Node.js 后端代码、生成或更新 PostgreSQL schema 与迁移、运行测试和验证，并汇总变更结果。

它不是“收到一句话就不经确认地改任何文件”。流程仍然是：

1. 用户提出需求，Team 帮助补全需求。
2. 用户确认需求。
3. Team 设计后端架构和数据库方案。
4. 用户确认方案。
5. Team 在批准范围内自动执行开发、测试和验证。

## 新项目和已有项目

- 新项目：在目标工作区创建 Node.js 后端基础结构、API、配置、schema、迁移和测试。
- 已有项目：先分析现有结构，再只修改设计确认中批准的文件和模块；不会因为项目已经使用 Node.js + PostgreSQL 就强制重建项目。

设计获批后，多文件修改可以连续执行，不需要用户逐文件确认；安装新依赖、应用数据库迁移、删除文件等高风险动作仍有独立确认门禁。

## 明确不会自动做的事

- 不连接或修改生产数据库。
- 不执行生产部署。
- 不写入批准工作区之外的路径。
- 不修改系统全局 Node、Python、uv、PostgreSQL、Shell 配置或系统服务。
- 不把数据库 GUI 的原始操作直接当作项目迁移；schema 变更必须先生成可审查的迁移。

## 当前实现状态

启用 `productionHost` 的本地 Profile 使用真实会话认证、团队工作流和受控执行。未配置生产宿主的默认安装仍只提供诊断能力。发布和平台验证范围以 [兼容性发布证据](../compatibility/release-evidence.md) 为准。

## 在对话中使用

在目标工作区的普通对话中描述功能、约束和预期结果，Agent 会创建独立团队任务。需求和设计先在聊天中展示，点击明确确认后推进；有修改意见时直接在聊天中提出，团队会撤回旧版本并生成新的待确认方案。

方案确认后，团队自动生成执行计划，开发并运行检查。数据库按任务需要准备，迁移仍须审查批准。无需在面板手动启动各个开发步骤。

“团队进度”是会话内的独立页签，用于查看当前阶段、待确认内容、执行记录和验收报告，不覆盖左侧会话列表。环境操作收在“人工接管”中。

交付后直接提出下一项需求即可创建新任务；已有任务记录保留。同一工作区同时运行一项未完成任务，避免两个任务交错修改业务文件。服务重启后沿用已保存的任务和审批版本，未完成阶段可在对话中请求继续。

### 运行循环、预算与恢复

开发 Agent 的墙钟预算从调度任务开始计时，包含 Agent 创建、模型连接和结果收集阶段；超时会先取消当前 Agent，再把本次超时墙钟用量写入工作区预算账本。账本会保留 `blocked:budget-exhausted`、实际用量和耗尽维度，重启后的调度器继续读取该终态，不能用同一任务 ID 静默重新注册。

Agent 返回的用量也会在交付前按任务预算复核。声明用量超过上限时，运行记录标记为受阻并保留观察到的用量；刚好达到上限的成功结果仍可通过，只有超时或实际超额才会进入受阻状态。

每个已通过的垂直切片在下一片开始前写入检查点。恢复只跳过有持久化交接证据的 `passed` 切片，并按依赖顺序继续；未通过或未验证的切片不会因已有输出文件而被当作完成。开发运行租约覆盖加载计划、执行和最终验证，`wait` 读取实际运行状态，运行中不会建议 `continue`，运行结束或锁被释放后才给出恢复或继续处置。

自动验收使用设计中批准的测试文件和证据对应关系。文件边界检查由宿主比较开发前快照；它证明配置目录中的文件保护情况，不代表已执行生产部署、外部服务或既有接口的运行时回归检查。

宿主另行完成的检查可通过 `.backend-team/task-evidence/<taskId>-review.json` 记录审查结果（文件权限 `0600`）。记录须绑定当前 `planHash`，`reviewedReports` 只能补充已批准的宿主证据 ID，并提供实际执行报告及其 SHA-256；`resolutions` 逐项绑定原待处理内容的摘要和审查理由。最终验证仍检查原生工作区边界、报告与文件摘要，仅在证据有效时解除对应待处理项，不改写 Agent 原始交接记录。

## 方案确认与任务资源

聊天里只展示简短摘要。右上角“任务资源”打开原生右侧栏，按方案文档、开发产物、验收报告分类预览；支持刷新和同一会话内历史任务切换。关闭资源恢复 DSH 工具详情，不覆盖会话列表。开发产物来自已保存交接记录中的文件列表；不提供任意本机文件浏览。

需求或设计的确认卡含“补充意见（选填）”。留空可直接确认当前版本；填写后提交给团队修订，修订后再次确认。稍后处理保持方案待确认。用户回答返回后会重新检查任务、修订号和文档摘要，旧回答不能批准新版本。

待确认业务问题使用 DSH 原生逐题问答，支持选项和自定义答案。需求文档中的 `backend-team:questions` JSON 注释记录当前未决问题，已回答问题在修订时移出；其他必须由用户决定的问题可由 `backend_team_workflow` 的 `ask` 操作提交，一次最多四题。答案完整收集后交给团队更新方案，不由模型代替用户选择。

### 并排审阅与 A2UI 表现层

方案审批从聊天底部表单移到右侧任务资源区。聊天只显示“查看并确认”入口，
打开资源不会使用遮罩；关闭资源保留当前等待请求的意见草稿。填写意见后，
“确认通过”禁用，只能提交修改意见；提交回答或意见不等于批准方案。
团队问题逐题显示于聊天输入框上方，支持上一题、下一题、稍后回答、补充说明和整组提交。
正常输入框继续使用 rc.6 已挂载的原生 composer fallback；没有新增第二套聊天输入实现。

表现层采用 A2UI v0.9.1 信封和自定义目录 `urn:dsh:backend-team:catalog:1`。
这是有意限制的 A2UI 子集，不是任意目录或完整 A2UI 引擎：

| 组件 | 本地映射 |
| --- | --- |
| Text、Badge | 文本与状态标签 |
| Column、Row | 有界布局 |
| Button、TextField | shadcn/ui Button、Textarea 的宿主 React 适配 |
| ChoicePicker | 带标签的原生单选控件，沿用统一主题 |

Agent 可以在 `backend_team_workflow` 的可选 `ui` 参数中输出两条消息
`createSurface`、`updateComponents`，使用 Text、Badge、Column、Row 说明方案。
交互控件由宿主从实际问题和待审批状态生成，Agent 不得自行生成审批按钮。
所有描述都经过目录、大小、图深度、重复 ID、循环引用和未知字段校验。
不接受 HTML、脚本、函数调用、任意 URL、远程目录或模型提供的事件处理代码。
允许的动作是 open-review、approve、submit-feedback、defer、previous、next、submit-answers；
这些名字只路由到本地固定处理器，不代表执行授权。暂停任务仍走原有 DSH control 服务。

审批前重新读取后端状态与受校验的 `open-artifact` 文档；实际回答走原生 wait.respond，
后端继续核对 session、task、revision、approvalId、artifactHash。前端只收到 wait 接收确认时，
文案为“确认已提交”，不会提前声称业务审批已经完成。持久化审批记录来自后端状态。

资源区每五秒更新实际任务信息，手动刷新仍可用。待审批文档首次查看建立本机比较基线，
后续版本在 `.backend-team/review-history/` 留存最近两份有界方案文档，支持查看真实变更片段。
旧版本尚无记录时明确提示，不合成变化摘要；开发代码和凭据不进入该历史。
浏览器关闭资源保留内存草稿，刷新页面会清除未提交草稿。

## TypeScript 测试支持与限制（2026-09-10）

正式受控测试工具、已批准测试方案的证据绑定和最终验收现在均接受 `test/`、`tests/` 下的 `.js/.mjs/.cjs/.ts/.mts/.cts` 文件。使用现有 Node 24 原生类型擦除执行 TypeScript，不安装额外加载器；相对导入需明确文件扩展名，类型导入使用 `import type`。

这不运行 TypeScript 类型检查，也不应用 tsconfig 路径别名或编译转换；JSX、装饰器、枚举、参数属性等需要转换的语法不能因此视为已支持。不能为了运行测试擅自替换原项目框架。最终报告明确写出“未验证类型检查、通用构建、部署或外部服务”。

仍只允许读取声明的文件，禁止文件写入、子进程和外网访问；保留 loopback HTTP 测试。验证证据绑定当前计划及文件摘要，编辑后旧证据失效。测试无用例、执行失败或语法不支持不能标记交付成功。

本轮 6 个相关测试文件 50 项通过，包含真实 macOS 受限进程下三种 TS 扩展名的开发/最终执行、审批证据到最终验收、失败断言、旧摘要拒绝和权限回归；完整构建、类型检查和相关 ESLint 通过。已安装本地 web profile。这些隔离测试不代表用户客户跟进任务已完成。

## 产物凭据检查（2026-09-10）

开发 Agent 已注册 `backend_team_scan`，只能检查其声明可读的单个文件，沿用工具预算、身份、阶段、宿主文件策略及当前审批检查。输出仅含状态、文件、行号和问题类型，不返回凭据正文或片段。

最终验收自动扫描计划声明的产物快照（不扫描方案说明文档），发现常见明文凭据或私钥时先停止测试执行并保存受阻报告。用户可查看文件位置，团队修复后重新验收；旧结果恢复时重新扫描当前产物，不因历史报告缺少该检查就恢复为交付成功。受阻报告本身仍可恢复查看。

检查复用本地 SecretScanner 的确定性规则，不联网，不等于完整安全审计、依赖漏洞扫描或认证正确性验证。可能识别出测试夹具中的仿真凭据，当前没有自动豁免或自动删除；需改用不会包含凭据字面量的测试输入。运行时网络权限仍由原执行策略管理。

验证：7 个相关文件 34 项测试通过；覆盖凭据不回显、报告数量限制、文件/身份/审批边界、测试执行前拦截、修复后重验以及历史报告恢复。完整构建、类型检查、相关 ESLint 通过，最后调整后再次完成 bundle 构建/类型检查。已安装本地 web profile；未执行用户业务审批或开发。

## 受限文件类型检查（2026-09-10）

开发专家现在可调用 `backend_team_typecheck`，参数为 `files`（任务声明内的 TS 源文件列表）。工具使用打包的现有 TypeScript 和 Node 类型声明，不安装项目依赖；仅可读取任务声明的普通文件及宿主编译器/标准类型，沿用身份、工具预算、commandExecution/readProjectFiles 能力、宿主文件策略和审批复验。

固定参数：noEmit、strict、ES2022、ESNext、bundler、allowImportingTsExtensions、Node types。忽略项目 tsconfig，不运行源代码、构建插件或项目脚本；沙箱禁止写文件、外网和子进程。未声明的相对依赖会导致检查失败。输出真实 argv、退出码、诊断和范围说明。

这是文件级检查工具，尚未替代项目自身 typecheck 命令；不能将其通过当作全量项目配置检查通过。设计显式选择后可成为最终验收门槛（见下节）。原有 Node 测试与需求证据对应关系保留；项目配置与通用命令审批仍待接通。

验证：3 个相关测试文件 9 项通过，包括真实编译器发现 TS2322、禁止未声明读取、不执行顶层写文件、不生成产物、能力拒绝及脱离开发仓库后的正式插件工具调用。完整构建/类型检查、相关 ESLint 通过；精简打包资产后重新运行 bundle 构建、类型检查和全部相关测试。包内确认含编译器、类型定义及许可证；工具版本保存在 lib/tooling/versions.json。已安装本地 web profile，未代用户执行真实业务审批或开发。

## 已批准类型检查的交付门槛（2026-09-10）

测试方案可在设计批准前声明一条文件列表，例如：

`<!-- backend-team:typecheck files=src/orders.ts,test/orders.test.ts -->`

最多 20 个不重复的 TS 源文件，必须同时属于执行计划产物。方案正文须说明固定严格配置、检查范围及其与项目全量检查的区别；不适配现有项目配置时不得强行采用。规划器保留已批准列表，不自行增加、删除门槛。声明缺失的旧方案保持原有验收行为；重复、空值、目录或未声明文件会被拒绝。

最终验收在凭据检查后、Node 测试前自动运行该列表。退出码非零、执行异常或审批失效均不能交付成功；报告保存命令、诊断、文件列表和范围，修复后重新运行。验收结束继续检查计划文件摘要，恢复 ready 结果时要求对应类型检查成功证据完整。受阻报告保留供审阅。

验证：4 个相关测试文件 47 项通过，含真实 TS2322 阻断后续测试、修复后验收通过、恢复时拒绝缺失成功证据、异常声明及既有验收回归。完整构建、类型检查、相关 ESLint 通过，更新安装至本地 web profile。未修改或批准用户真实任务；完整客户跟进交付和项目级配置检查仍未验收。
