# DeepSeek Harness client/host evidence

Official documentation now identifies the public Web Client surfaces used by a future production Bundle:

- `ctx.clientModules` is the host-side `ClientModuleRegistry`; packages declaring `dsh.client` are scanned and served as `/plugins/<id>/client.js`.
- A browser package exports `./client`, declares `dsh.client`, and receives a `ClientContext` from `@deepseek-ai/dsh-client-runtime/client`.
- A conversation business row registers a `ConversationNodeDefinition` through `conversationEvents` and a keyed renderer through `slots.inject('conversation.chat.node', ...)`.
- A frame-wide feature surface uses the additive `shell.overlay` list slot; registering
  into `conversation` or `details` would replace the shipped surface rather than add
  to it. The Bundle declares `@deepseek-ai/dsh-client-ui-layout` so this slot is
  present before its overlay registration runs.
- Browser client assets are classic scripts that call
  `window.__ModuleLoader__.load({ id, factory })`. The Bundle builds its `./client`
  entry as a lazy CJS factory and resolves the Harness-provided React singleton at
  materialization time; it does not ship a second React runtime.
- Host-side HTTP routes use `ctx.webServer.register(route)` and must explicitly bind `127.0.0.1` when local-only.
- The explicit production helper includes `createDshLocalSessionInput()`: it
  consumes the route's query `sessionId`, then checks the live rc.6
  `ctx.sessions.get()` and `ctx.agents.get()` entries plus the session header's
  canonical `cwd` before producing the authenticated-local-session record. The
  helper is opt-in and rejects missing stores, non-loopback callers, unknown
  sessions, and cross-workspace sessions.
- Agent creation is owned by `ctx.agents`; the public creation result is an `AgentHandle` with `agent` and `dispose()`.

The Bundle now also exposes explicit rc.6 port adapters.
`createVerifiedDshHostPort()` requires the documented
`ctx.webServer.register()` method and a `ctx.webServer.host` value of
`127.0.0.1`; `createVerifiedDshSessionPort()` binds the same context's exact
Session and Agent stores to the per-request extractor;
`createVerifiedDshAgentPort()` binds the existing Agent runtime adapter to
`ctx.agents.create()`. `createDshProductionHost()` composes those verified Host
and Session ports with the existing production activation. These are
source-compatible structural adapters, not a claim that the diagnostic Bundle
has been promoted to writable mode.

`npm run verify:dsh-production-ports` now runs a disposable workspace-local
`web` Profile and has observed all three markers from the real rc.6 Cordis
context: `webServer.host` was `127.0.0.1`, and Host/Session/Agent adapters each
reported `verifiedProvenance: true`. This proves the adapter boundary and
loopback binding only; it does not execute a production coordinator or model
request.

The application control service does not treat a browser-provided session object as proof of identity. It requires an injected `LocalSessionAuthenticator`; the Zod session schema is applied only after that host-owned authentication boundary.

The web package now contains a host-neutral `applyBackendTeamControlRoute()`
adapter for the proven `ctx.webServer.register({ kind: 'prefix', path,
handler })` contract. It exposes only loopback `state` and `dispatch` paths,
limits JSON bodies, maps control errors to bounded HTTP responses, and requires
the host to provide the session-input extractor. This adapter is not mounted by
the default diagnostic Bundle; a real host must still supply the authenticated
session source and coordinator action handlers before production activation.

Its `createBackendTeamControlSurface()` companion installs the persisted-event
subscription before replay, buffers events arriving during the initial read,
and publishes only validated monotonic projections to the subscription hub.

The Bundle's explicit `createBackendTeamProductionHost()` now composes those
application-owned pieces only after the activation gate succeeds. It requires
the host to provide the complete coordinator action table and authenticated
session extractor, registers the route only in supported mode, and disposes the
route, subscriptions, and production composition in reverse order. This is a
host-neutral assembly helper, not proof that rc.6 itself supplies those
coordinator/session capabilities.

The database package now provides `createDatabaseExecutionPort()`. It accepts
already-constructed workspace-local PostgreSQL and optional DbGate lifecycle
objects, enforces loopback-only GUI navigation with an expiry, and provides
idempotent reverse-order disposal. Passing that verified port as `databasePort`
fills the production host's three revision-fenced database commands; no raw
executable, credential, or arbitrary SQL surface is exposed.

The web package also exposes a host-neutral `createBackendTeamControlClient()`
bridge. Its transport is injected by the host, so it stores no credentials and
does not assume a particular HTTP client. It validates the projected state and
command response, rejects stale revisions locally, requires the current
approval artifact to be inspected before a decision, and refreshes the
authoritative state after an accepted command. Pushed snapshots and refreshes
are monotonic, so a delayed response cannot roll the panel back. Server-side
revision and approval checks remain mandatory.

Sources: [client modules](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/client-modules), [Conversation Node guide](https://deepseek-harness.github.io/deepseek-harness/en/reference/cookbook/adding-a-conversation-node), [Core agent lifecycle](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/core), and [HTTP server](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/web-server).

The workspace-local rc.6 runtime has now been inspected and its public declaration hashes plus a real Profile smoke are recorded in [the fixture](./0.1.0-rc.6-client-host-fixture.json). The repeatable `npm run verify:web-client` check additionally installs the packed Bundle into an isolated Web Profile, verifies the loopback root, parses `window.__DSH_BOOT__`, and fetches the Bundle client asset. The packed-bundle gate also evaluates the classic-script handoff and invokes the factory with a React/module-table double. Codex Chrome has separately verified client materialization and overlay rendering; the full browser control-flow acceptance remains `not-run` because diagnostic mode intentionally has no production route.

The Agent lifecycle and session-event probe is recorded separately in [the Agent runtime fixture](./0.1.0-rc.6-agent-runtime-fixture.json). It proves public Agent creation, the workspace `HarnessAgentRuntime` result boundary against a local model stream, host-side usage conversion, and disposal; production Bundle/coordinator composition and a real DeepSeek credential request remain unproven.
