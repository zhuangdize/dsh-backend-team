# DeepSeek Harness Agent runtime evidence

The repeatable `npm run verify:agent-runtime` check builds the workspace adapter and runs in a disposable rc.6 `headless` Profile. Its observer registers a local test LLM adapter through the public `ctx.llm` service, routes the official `ctx.agents` registry through the project's `HarnessAgentRuntime`, creates an Agent through `ctx.agents.create()`, sends one identified user message, waits for `agent.whenIdle()`, decodes the resulting `assistant/message` session event and its optional usage record, then confirms the returned handle is disposed.

The observed public shape is recorded in [the fixture](./0.1.0-rc.6-agent-runtime-fixture.json): the returned `AgentHandle` contains `agent` and `dispose()`. The Agent exposes `id`, `status`, `options`, `session`, `cancel()`, `whenIdle()`, and `followup()`. The durable session log is the result source; `assistant/message.data.usage` is the token-usage source. Disposal removes the session from `ctx.agents`.

The host-neutral `HarnessAgentRuntime` adapter now implements the application `AgentHandle` boundary. It serializes the coordinator task into one identified user message using the official `@deepseek-ai/dsh-llm/message` constructor (so the Harness receives a generated `id`, fixed `role: 'user'`, and plugin source metadata), maps a scheduled `agentTask.budget.maxTokens` into the official Agent option, waits for the matching assistant event, exposes a host usage summary to an explicitly supplied decoder, and makes result/cancel disposal idempotent. The application-level `decodeHarnessAgentResult` decoder accepts only structured `AgentResult` JSON and replaces model-reported usage with host usage. Both pieces are exported for the eventual Bundle composition but are not enabled by the diagnostic-only Bundle yet.

The adapter accepts optional `provider` and `model` values. When the Bundle omits them, it forwards only the task budget and lets the official Harness choose its configured default model, including a Codex-authenticated provider; the Bundle does not require a second LLM endpoint or credential.

The application production port now persists a `run-recorded` event when a verified handle starts, including the bounded terminal `ConsumedBudget` before returning a completed result; cancellation records an `interrupted` run. Result reads are coalesced so concurrent callers cannot trigger duplicate underlying Agent reads or terminal events. If the start event cannot be persisted, the newly spawned handle is cancelled before the spawn call returns. This is an application-owned event guarantee, not a new Harness API claim. The checked-in fixture remains partial because the Bundle/coordinator composition is still not wired and has not been proven in a fresh Profile; the scheduler's parent/child reservation recovery is covered by application integration tests.

Approval requests also carry the caller's current application state revision into the pending approval record, so a later decision can be rejected when the browser is stale. The revision field belongs to the application orchestration contract and is intentionally not attributed to the Harness Agent API.

This is deliberately a partial compatibility result. The local adapter and application tests prove the lifecycle, structured `AgentResult` mapping, bounded usage conversion, and workspace-local scheduler recovery without requiring credentials, but they do not prove production Bundle/coordinator composition, a real DeepSeek network request, or browser E2E. Browser E2E and release therefore remain blocked. See the official [Core agent lifecycle](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/core) documentation for the public `ctx.agents` contract.

Both release entry points fail closed on this status: `scripts/build-release.mjs` and `scripts/verify-release.mjs` require this fixture to be `verified` with an empty `notProven` list, otherwise they return `INCOMPLETE_AGENT_RUNTIME_PROVENANCE`. This keeps a future native PostgreSQL artifact from accidentally promoting the still-diagnostic Bundle into a production release.
