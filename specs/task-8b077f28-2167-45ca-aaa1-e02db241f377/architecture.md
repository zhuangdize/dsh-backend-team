# 人员管理功能 架构设计

## Context
需求基线见同目录 `spec.md` 与 `clarification.md`：完整入转调离（Q1）、仅 HR 管理员（Q2）、本系统自维护无外部同步（Q3）、仅基础与雇佣信息（Q4）。
技术前提（仓库证据）：monorepo + Node + TypeScript strict + PostgreSQL/Drizzle 迁移 + Vitest/`node:test`。
明确未确认项：承载本功能的宿主包与服务边界（宿主检查 `serviceBoundary=null`、`service-boundary-ambiguous`）。因此本设计将领域逻辑收敛在单一内聚模块内，使落地位置可在实施开始前确认；不替换既有代码、不新建重复的人员存储。

## Module Boundaries
人员模块（`personnel`）对内四层，对外一个只读接口：
- `api`：路由、DTO 与参数校验、HTTP 状态映射；不含业务规则。
- `domain`：规则 R1–R7 的可单元测试实现——工号唯一且不复用、状态机（草稿→在职→停用）、任职区间不重叠、汇报关系无自引用/无环、停用不可指派。
- `persistence`：Drizzle schema 与仓储，事务边界在此层；迁移文件独立。
- `audit`：字段级前后值 + 操作人 + 时间 + 生效期间的追加写；界面与常规接口无更新/删除路径（R7）。
对外：下游业务模块只通过只读查询接口取身份、组织归属与在职状态，不直接读表（spec Integrations）。组织与岗位本迭代以「标识 + 名称快照」存储，不提供组织主数据管理接口（需求未定义该流程）。

## Request Flow
写入：认证中间件解析调用者 → 角色门禁（仅 HR 管理员）→ DTO 校验（中文可理解提示，R6）→ domain 校验（唯一性、区间重叠、汇报环）→ 单事务内写主档案/任职记录 + 追加变更记录与审计 → 读取视图返回。
读取：默认在册视图 = 状态在职且在生效区间内；支持姓名/工号/部门/状态筛选与分页（F2）；字段级过滤在服务端完成。

## API and Authentication
契约见 `contracts/openapi.yaml`（资源前缀 `/persons`：建档、列表、详情、在职变更、任职变更与撤销、状态流转、历史、受限删除）。
认证复用宿主既有会话机制（Cookie 或 Bearer，实施时按宿主确认，不新增独立登录体系）。授权是服务端强制的：集合与写操作对非 HR 返回 403；人员维度资源对非 HR 返回 404，与「记录不存在」不可区分，避免泄露存在性（AC-008）。界面隐藏不作为控制手段。

## Failure Model
- 400：必填缺失/格式非法，返回字段级中文错误（AC-001、R6）。
- 409：工号冲突（AC-002）、任职区间重叠（AC-005）、非法状态流转（R2）、被业务引用档案的删除请求（AC-007）。
- 404：不存在或无权访问的人员维度资源。
- 503：数据库不可用。
所有写操作在同一事务内完成，任一步失败（含审计写入失败）整体回滚，不产生半写状态；无物理级联删除，停用为状态变更。撤销仅对尚未生效的变更有效。

## Observability
- 结构化日志：请求 id、调用者 id、动作、目标人员 id、结果码与触发规则；不记录字段值与联系方式等个人数据。
- 指标：请求量/延迟分布、按规则归类的拒绝计数（重复工号、区间重叠、越权）、审计写入失败计数。
- 追溯：任一人员的历史即审计视图，可还原「谁在何时改成了什么」（AC-010）；性能与容量阈值未经业务确认，本稿不设数字目标。
以上均沿用宿主既有日志/指标通道，不引入新的可观测后端。

## Alternatives
- 拆为独立人员微服务：边界未确认时成本与风险更高，弃用。
- 事件溯源作为时间轴主存储：字段级历史 + 任职区间已满足 Q1，复杂度不必要，弃用。
- 仅软删除、不提供删除接口：AC-007 要求「引用守护下的删除」语义可验证，故保留受限删除。
- 对接外部人事/通讯录：Q3 明确排除。

## Risks
- 宿主包与路由挂载点未确认，迁移目录与模块路径可能在实施前调整。
- 认证与角色来源（HR 管理员如何标识）依赖宿主既有机制，需实施前确认。
- 下游「业务引用」的判定依赖既有模块，AC-006/AC-007 需真实引用点才能完整验证。
- 审计不可改写依赖数据库账号权限，尚未验证。
- 检测到的构建/lint/typecheck 脚本均未执行；AC-011 由宿主在后续阶段按计划内测试执行并记录。
