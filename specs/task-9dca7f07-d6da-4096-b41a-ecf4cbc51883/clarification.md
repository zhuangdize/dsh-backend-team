# 需求澄清记录：客户管理功能

原始需求："做一个客户管理功能，支持新增、查询和修改客户信息。" 未指定字段清单、权限模型与删除等行为。本轮需求范围保持不变。

## Session 2026-09-13（Q1–Q3 已定稿）

- Q: 客户字段的权威清单是什么？是否需要在名称/联系人/电话之外加入统一社会信用代码、客户来源、负责人归属、地区等字段？ → A: 沿用当前最小集合（推荐）
- Q: 重复判定的唯一键采用哪种？ → A: 联系电话唯一（推荐）
- Q: 是否需要区分修改权限角色？ → A: 授权人员均可改全部客户（推荐）

## 已确认结论

| 疑问 | 回复 | 定稿口径与对需求的影响 |
| --- | --- | --- |
| Q1 字段权威清单 | 沿用当前最小集合 | 必填：名称、联系电话；可选：联系人、邮箱、公司、备注。不加入统一社会信用代码、客户来源、负责人归属、地区等字段；清单外字段不接受、不静默写入。已写入 spec.md Rules / Data and Privacy / Non-Goals；AC-001、AC-002 的字段与校验口径不变，仅把"必填仅名称+电话"写明。 |
| Q2 重复判定唯一键 | 联系电话唯一 | 电话归一化后在全系统唯一即最终判重依据；冲突拒绝新增并提示已存在客户。AC-003 已明确覆盖不同书写形式（带分隔符与纯数字视为同一号码）。 |
| Q3 修改权限角色 | 授权人员均可改全部客户 | 不区分资料录入人，也不设只读角色；两个权限点（查看、维护）即为全部粒度。AC-006 补充"非录入人可改且记录实际操作人"，AC-010 补充"结果不因客户创建者不同而不同"；AC-008 并发语义不变。 |

同时修正本文档早期表述：曾把"联系人"列为必填，与 spec.md Rules 及已批准契约不一致；按 Q1"沿用当前"的回复，以 spec.md 为准，`contactPerson` 为可选字段。

## 已解决的疑问（沿用合理默认，本轮无变化）

| 疑问 | 结论与理由 |
| --- | --- |
| 是否支持删除？ | 本期不支持删除、合并与回收站，归入 Non-Goals（原始需求只列了新增、查询、修改）。 |
| 并发修改如何处理？ | "先查询后保存"，检测到他人已更新时拒绝保存并提示刷新，避免静默覆盖。 |
| 查询能力到什么程度？ | 关键词匹配（名称/联系人/电话）+ 分页 + 总数 + 详情页；不做复杂筛选与排序配置。 |
| 变更留痕？ | 记录变更人、变更时间、字段前后值；手机号/邮箱前值脱敏。 |
| 是否批量导入/导出？ | 本期不做，已列为 Non-Goal；如业务需要扩展再单独立项。 |
| 性能与规模 | 团队级内部系统的常规预期：查询 2 秒、写入 3 秒内响应；未虚构高并发指标。 |

## 仍需确认的问题

无。三项业务选择均已回复并写回 spec.md，验收标准 AC-001–AC-010 的编号与数量保持不变（仅收紧表述，未新增功能）。剩余事项属于团队可在计划与实现阶段自行确定的技术细节，不需要业务方决策，例如：上游会话 Cookie 名称与身份桥接方式、目标数据库版本与迁移工具、号码归一化的具体规则实现、翻页排序键选型与是否启用 `pg_trgm`。这些已在既有 research.md / decisions.md / data-model.md 中列为实现期确认项，不作为需求未决问题。
